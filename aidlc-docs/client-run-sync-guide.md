# 러닝 기록 전송 가이드 (클라이언트용)

> **대상**: iOS / 프론트엔드 구현자
> **다루는 것**: 러닝 기록을 서버에 올리는 전 과정 — 특히 **비로그인 상태로 달린 기록을 가입 후 올리는 흐름**
> **API 스펙 원본**: `API.md` §7. 이 문서는 "어떤 순서로, 무엇을 저장해뒀다가, 어떻게 보낼지"를 다룹니다.

---

## 1. 결론 먼저

| 상황 | 처리 |
|---|---|
| 로그인 상태로 달림 | 러닝 끝나면 바로 `POST /runs` |
| **비로그인 상태로 달림** | **기기에 캐시 → 로그인/가입 직후 업로드** |
| 업로드 실패 | 캐시에 남겨두고 다음 기회에 재시도 (**같은 `clientRunId` 로**) |

서버는 비로그인 기록을 받지 않습니다(`/runs` 는 전부 인증 필요). 그래서 **기기가 임시 보관소** 역할을 합니다.

---

## 2. 왜 이 방식인가

검토한 대안과 탈락 이유입니다.

| 방안 | 판단 |
|---|---|
| 러닝 시작 전 로그인 강제 | 여행지에서 앱을 처음 켠 사용자에게 진입 장벽. 이탈 지점이 최악 |
| 비로그인 기록은 그냥 버림 | **첫 러닝을 잃음.** "다 달렸는데 기록이 없네"가 체감상 가장 나쁨 |
| 서버에 익명 계정으로 저장 후 병합 | 서버 구조를 뒤집어야 하고, 병합 버그 시 **남의 기록이 섞일 위험**. 기기를 바꾸면 어차피 복구 불가라 이득이 적음 |
| **기기 캐시 후 업로드** ✅ | **서버 변경 0.** UX는 익명 계정 방식과 사실상 동일. Strava·나이키런클럽도 같은 방식 |

---

## 3. 전체 흐름

```
러닝 종료
   │
   ├─ 결과 화면 표시 (서버 없이 가능 — 거리·시간·페이스·지도는 전부 기기가 가진 값)
   │
   ├─ 로그인 상태?
   │    ├─ YES → 바로 업로드 (5번)
   │    └─ NO  → 캐시에 저장 (4번) + "로그인하면 기록이 저장됩니다" 안내
   │
   └─ (나중에) 로그인/가입 성공
            └─ 캐시를 오래된 순으로 하나씩 업로드 → 성공한 것만 캐시에서 삭제
```

> 비로그인 결과 화면에는 **업적 도장이 없습니다.** 업적은 사용자별로 판정되므로 로그인 전에는 계산할 수 없습니다.
> 나중에 업로드하면 그때 판정되어 도장이 나옵니다.

---

## 4. 캐시에 저장할 항목

**하나라도 빠지면 나중에 올릴 때 정보가 손실됩니다.**

| 항목 | 타입 | 왜 필요한가 |
|---|---|---|
| `clientRunId` | String (UUID) | **중복 저장 방지.** 러닝이 끝난 시점에 **한 번** 만들어 저장. 재전송 때도 같은 값 |
| `startedAt` | ISO8601 | 없으면 "얼리버드"(한국시간 08시 이전 시작) 업적을 못 받음 |
| `finishedAt` | ISO8601 | **없으면 달린 날짜가 아니라 "업로드한 날짜"로 기록됨** |
| `distanceMeters` | Int | |
| `durationSeconds` | Int | |
| `calories` | Int? | 소모 칼로리(kcal). 있으면 같이 저장해 두세요 — 나중에 올릴 때 다시 계산할 수 없습니다 |
| `start` / `end` | {lat, lng} | 출발·도착 좌표 |
| `courseId` | String? | 공식 코스를 달렸을 때만. **업적 9종의 판정 기준** |
| 이미지 파일 경로 | String | 코스 이미지. 업로드 시 필수 |

### ⚠️ `clientRunId` 는 러닝 종료 시점에 만드세요

```
❌ 업로드할 때 UUID 생성  →  재시도마다 값이 달라져 중복 방지가 무력화
✅ 러닝 종료 시 UUID 생성 → 캐시에 저장 → 재시도에도 같은 값 사용
```

### ⚠️ 이미지는 파일시스템에, 경로만 캐시에

- 웹뷰 `localStorage` 는 5~10MB 한도이고 base64 로 넣으면 용량이 1.33배가 됩니다
- 러닝 몇 건만 쌓여도 한도를 넘습니다
- **파일은 앱 저장소에 두고 캐시에는 경로만** 보관하세요

### 캐시 항목 예시

```json
{
  "clientRunId": "7f3a9c2e-4b1d-4e8a-9c3f-2a1b5d6e7f80",
  "courseId": "gunsan-jjamppong-run",
  "start": { "lat": 35.95, "lng": 126.68 },
  "end":   { "lat": 35.96, "lng": 126.69 },
  "distanceMeters": 10480,
  "durationSeconds": 3600,
  "calories": 720,
  "startedAt":  "2026-09-13T07:00:00Z",
  "finishedAt": "2026-09-13T08:00:00Z",
  "imagePath": "file:///.../runs/7f3a9c2e.jpg"
}
```

## 5. 업로드

```
POST /runs
Authorization: Bearer {accessToken}
Content-Type: multipart/form-data
```

파트 2개: **`run`**(JSON) + **`image`**(파일). 둘 다 필수입니다.

```bash
curl -X POST https://dallyeo.cloud/runs \
  -H "Authorization: Bearer $TOKEN" \
  -F 'run={"clientRunId":"7f3a9c2e-...","courseId":"gunsan-jjamppong-run","start":{"lat":35.95,"lng":126.68},"end":{"lat":35.96,"lng":126.69},"distanceMeters":10480,"durationSeconds":3600,"calories":720,"startedAt":"2026-09-13T07:00:00Z","finishedAt":"2026-09-13T08:00:00Z"}' \
  -F "image=@route.jpg"
```

### 알아둘 점

- **`run` 파트에 `Content-Type` 을 붙이지 않아도 됩니다.** 생략하든 `application/json` 이든
  `application/octet-stream` 이든 동일하게 동작하도록 서버가 처리합니다.
- 좌표 키는 **`lat` / `lng`** 입니다. `latitude`/`longitude` 가 아닙니다.
- 이미지 형식: JPEG / PNG / WebP / HEIC / HEIF, **최대 10MB**.
- `averagePaceSeconds` 는 **보내지 않습니다** — 서버가 거리÷시간으로 계산해 응답에 담아줍니다.
- `calories` 는 반대로 **보낸 값을 서버가 그대로 저장**합니다(HealthKit 값이 서버 추정보다 정확).

### 응답 (201)

```json
{
  "success": true,
  "data": {
    "id": 1,
    "courseName": "짬뽕런",
    "start": { "lat": 35.95, "lng": 126.68 },
    "end":   { "lat": 35.96, "lng": 126.69 },
    "distanceMeters": 10480,
    "durationSeconds": 3600,
    "averagePaceSeconds": 344,
    "calories": 720,
    "imageUrl": "/uploads/runs/fb63bae3-....jpg",
    "startedAt":  "2026-09-13T07:00:00Z",
    "finishedAt": "2026-09-13T08:00:00Z",
    "newAchievements": [ /* 이번에 처음 딴 업적 */ ]
  }
}
```

> 값이 없는 필드는 **키 자체가 응답에서 빠집니다**(`null` 로 오지 않음).
> `courseId` 없이 저장하면 `courseId`·`courseName` 키가 아예 없습니다. 존재 여부로 판단하세요.

## 6. 여러 건을 한꺼번에 올릴 때

로그인 직후 캐시에 여러 건이 쌓여 있을 수 있습니다.

### ① 반드시 오래된 순서로

누적 조건 업적(`FINISH_10` 완주 10회, `DISTANCE_100KM` 누적 100km)이 **저장 순서를 탑니다.**
시간순으로 올려야 "10번째 러닝에서 완주 10회 달성" 같은 결과가 자연스럽게 맞습니다.

```
캐시를 finishedAt 오름차순 정렬 → 순차 전송
```

### ② 병렬 전송하지 마세요

업적 판정이 "그 시점까지의 전체 이력"을 보기 때문에, 동시에 보내면 판정 결과가 뒤엉킬 수 있습니다.
**하나 성공 → 다음 하나** 순서로 보내세요.

### ③ 도장은 응답마다 따로 옵니다

3건을 올리면 응답도 3개이고, 각각 `newAchievements` 를 가집니다.
결과 화면에 한 번에 보여주려면 **클라이언트가 합쳐야** 합니다.

```
실측 예시 (3건 순차 업로드)
  09-08 저장 → 🏅 LONG_RUN_3H, EARLY_BIRD
  09-09 저장 → (없음)
  09-10 저장 → 🏅 DISTANCE_100KM
  → 화면에는 3개를 모아서 표시
```

## 7. 실패·재시도 처리

### 중복 저장을 막는 원리

```
앱 → POST /runs → 서버 저장 완료 → 응답 전송 ─╳─ (네트워크 끊김)
앱: "실패했네" → 재시도
```

클라이언트는 **"저장 실패"와 "저장됐지만 응답 유실"을 구분할 수 없습니다.**
그래서 `clientRunId` 를 같이 보내면, 서버가 같은 키를 알아보고 **새로 만들지 않고 기존 기록을 반환**합니다.

```
1회차 (키 K) → id=1, 도장 3개
2회차 (키 K) → id=1, 도장 []     ← 새로 안 만들어짐
3회차 (키 K) → id=1, 도장 []
서버에 저장된 기록: 1건
```

> **중복 응답의 `newAchievements` 는 항상 `[]`** 입니다. 도장은 첫 요청에서 이미 처리됐고,
> 재전송이 다시 띄우면 "최초 1회만" 규칙이 깨지기 때문입니다.
> 응답 유실로 도장을 놓쳤다면 업적 목록(`GET /achievements`)에서 확인할 수 있습니다.

### 키를 안 보내면

중복 판정을 하지 않아 **재시도마다 새 기록이 쌓입니다.** 그리고:

- **러닝 삭제 API가 없어** 사용자도 앱도 지울 수 없습니다(서버 DB 직접 수정 필요)
- 누적 업적이 부풀려져 **안 딴 업적이 영구히 달성 처리**됩니다(업적은 취소 불가)

**로그인 여부와 관계없이 모든 저장에 `clientRunId` 를 보내세요.** 야외에서 사진이 붙은
multipart 를 전송하는 구조라 일반 로그인 사용자도 같은 위험을 겪습니다.

### 캐시 삭제 시점

```
201 응답 수신 → 캐시 항목 삭제 + 이미지 파일 삭제
그 외(타임아웃·5xx·네트워크 오류) → 캐시 유지, 다음 기회에 재시도
400 응답 → 캐시 유지해도 영원히 실패함 → 로그 남기고 폐기 판단
```

`400` 은 데이터 자체가 잘못된 경우라 재시도해도 계속 실패합니다. 아래 9번으로 원인을 확인하세요.

## 8. 로그인하지 않고 계속 쓰는 경우

- 캐시가 무한히 쌓이지 않도록 **보관 개수/기간 상한**을 두는 것을 권장합니다(예: 최근 20건 또는 30일)
- 앱을 삭제하면 캐시도 사라집니다 — 복구 방법이 없습니다
- 안내 문구로 로그인을 유도하되, 러닝 자체는 막지 않는 것이 이 설계의 전제입니다

---

## 9. 오류 응답

모든 실패는 아래 형태입니다.

```json
{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "..." } }
```

| HTTP | code | 원인 | 조치 |
|---|---|---|---|
| 400 | `VALIDATION_ERROR` | 필수 필드 누락, JSON 형식 오류, 이미지 파트 없음, 파일 형식/크기 위반 | 데이터 수정. 재시도해도 실패 |
| 400 | `BAD_REQUEST` | `finishedAt < startedAt` | 시각 확인 |
| 401 | `UNAUTHORIZED` | 토큰 만료/없음 | 토큰 갱신 후 재시도 |
| 500 | `INTERNAL_ERROR` | 서버 오류 | 재시도 대상 |

검증 실패 메시지는 **어느 필드가 문제인지** 알려줍니다:
```
"durationSeconds는 필수입니다. / end(도착 좌표)는 필수입니다."
"run 파트의 JSON 형식이 올바르지 않습니다: ..."
```

## 10. 체크리스트

구현 후 아래를 확인하세요.

- [ ] `clientRunId` 를 **러닝 종료 시점**에 생성해 캐시에 저장하는가 (전송 시점 아님)
- [ ] 재전송할 때 **같은** `clientRunId` 를 쓰는가
- [ ] 로그인 사용자의 일반 저장에도 `clientRunId` 를 보내는가
- [ ] `startedAt` / `finishedAt` 을 캐시에 저장하고 업로드 시 함께 보내는가
- [ ] `calories` 를 캐시에 저장하고 업로드 시 함께 보내는가 (나중에 재계산 불가)
- [ ] 이미지를 파일시스템에 저장하고 경로만 캐시에 두는가
- [ ] 여러 건 업로드 시 **오래된 순으로 순차** 전송하는가
- [ ] `201` 을 받은 뒤에만 캐시를 삭제하는가
- [ ] `newAchievements` 가 **0개일 수도, 여러 개(최대 7개)일 수도** 있다는 전제로 UI를 만들었는가
- [ ] 공식 코스를 달렸을 때 `courseId` 를 보내는가 (안 보내면 업적 9종 판정 불가)
- [ ] 응답에서 `courseName` 등이 **키 자체로 없을 수 있다**는 전제로 파싱하는가
