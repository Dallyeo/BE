## 2. ⚠️ 핵심 이슈: 좌표(위경도) 없음

34개 컬럼 중 **위도/경도(WGS84) 컬럼이 없음.** 주소(도로명/지번)만 존재.

**문제**:
- 화장실은 **편의시설**로 지도 마커·**반경 500m 주변 조회**(US-PLACE-3, 화면 V8/V10)에 노출해야 함 → **좌표 필수**
- 좌표 없이는 지도 표시·거리 계산 불가

**→ 주소 → 좌표 변환(지오코딩)이 필요.**

### 좌표 확보 방법 후보
| 방식 | 설명 | 장단점 |
|---|---|---|
| A. 지오코딩 배치(1회) + 좌표 캐싱 | 도로명주소를 지오코딩 API(카카오/Tmap/공공 Geocoder)로 1회 변환 후 DB에 좌표 저장 | 정석. 갱신 시만 재변환. API 키·비용·정확도 확인 필요 |
| B. 좌표 있는 데이터셋 재확보 | 위경도 포함된 다른 공중화장실 데이터로 교체 | 있으면 최선(변환 불필요). 없을 수 있음 |
| C. 좌표 없이 리스트만 | 지도 마커 없이 주소 리스트로만 제공 | 반경/지도 기능 포기 → 앱 요구(V8/V10)와 불충족 |

> 데이터 소량(718건)이라 **A(1회 배치 지오코딩 + 캐싱)** 가 현실적. 지번주소도 있어 지오코딩 실패 시 대체 시도 가능.

## 3. 데이터 모델 (제안)

- **독립 장소 테이블**(TourAPI place와 별개): `PublicToilet` 또는 통합 `Place(type=CONVENIENCE)`
  - 필드: name(화장실명), roadAddress, jibunAddress, **latitude/longitude(지오코딩 결과)**, openTime, 편의정보(장애인/어린이/기저귀/비상벨/CCTV), region
- **주변 조회 통합**: US-PLACE-3(반경) 응답에 TourAPI 장소 + 화장실을 **category로 구분**해 함께 반환
- region 매핑: 군산/전주 파일 → Region enum

## 4. 결정 필요 (❓) — ⏸️ **후순위(deferred)**

> **상태**: 화장실/편의시설은 **우선순위 낮음** → 지금은 분석만 남기고 결정은 보류. Workflow Planning 이후 필요 시점에 확정.

1. **좌표 확보 방식**: A(지오코딩 배치+캐싱) / B(좌표 데이터 재확보) / C(리스트만) 중 선택
2. **지오코딩 수단**(A 선택 시): 카카오 로컬 API / Tmap / 공공 Geocoder 등 — 키·비용 확인
3. **편의정보 노출 범위**: 장애인·어린이·기저귀교환대·비상벨·CCTV 중 앱에 표시할 항목
4. **적재/갱신**: 소량이라 파일 재업로드 시 수동 재적재 + 재지오코딩으로 충분?
5. **동일 이슈 확인**: 가로등/약국 등 다른 편의시설 데이터도 좌표 부재 가능성 → 같은 방식 적용 예정
