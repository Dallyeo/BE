# Requirements — Dallyeo (달려)

> 전라도 지역 기반 러닝 코스 서비스. 운영자가 등록한 코스를 달리거나 직접 코스를 만들고,
> 러닝 후 도착지 주변의 먹거리·편의시설·관광지를 추천/표시하는 모바일 앱 백엔드.

---

## 1. Intent Analysis (의도 분석)

| 항목 | 내용 |
|---|---|
| **User Request** | 전라도 지역 대상, 기존 러닝 코스 달리기 + 직접 코스 만들기, 러닝 후 먹거리 추천 및 주변 편의시설/관광지/음식점 표시 앱의 백엔드 구축 |
| **Request Type** | New Project (스캐폴딩만 존재하는 브라운필드 → 실질적 신규 구축) |
| **Scope Estimate** | System-wide (여러 도메인: 인증 / 코스 / 러닝 기록 / 장소 추천) |
| **Complexity Estimate** | Complex (외부 API 다수 연동 + 지리/공간 데이터 + 인증) |
| **Requirements Depth** | Comprehensive (앱 전체를 정의한 뒤 범위를 분할하기로 함) |

**이번 사이클 목표**: 요구사항 + 앱 전체 설계까지 완성. 코드 생성(구현)은 그 다음 사이클에서 결정. (Q18=A)

## 2. Domain Overview (도메인 개요)

- **대상 지역**: 전라도 전용 (지역 확장은 고려하지 않음 — Q17=B)
- **클라이언트**: 모바일 앱 (iOS/Swift + TypeScript 혼용 뷰). 백엔드는 **REST API** 제공 (Q7)
- **핵심 가치**: 지역 러닝 코스 제공 → 러닝 실행/기록 → 러닝 후 주변 먹거리·시설 추천

---

## 3. Functional Requirements (기능 요구사항)

### FR-1. 인증 / 회원 (Authentication)
- **FR-1.1** 소셜 로그인 기반 인증 (카카오, 애플 우선). 자체 이메일/비밀번호 가입은 범위 밖 (Q15=B)
- **FR-1.2** JWT 기반 인증: Access Token + Refresh Token. Refresh Token은 Redis 저장 (Q4=A)
- **FR-1.3** Access Token 만료 시간 = **24시간**. Refresh Token은 기존 7일 유지 (Q4)
- **FR-1.4** 소셜 로그인 외 소셜/커뮤니티 기능(팔로우/피드/공유)은 이번 범위 밖 (Q14=A)

### FR-2. 러닝 코스 (Course)
- **FR-2.1** 운영자가 미리 등록해 둔 **공식 코스**를 사용자가 조회/선택 (Q8=A, 시작 시점 코스는 운영자 데이터)
- **FR-2.2** 사용자가 코스를 **직접 생성** 가능. **Tmap API는 사용하지 않음** — 경로 생성은 클라이언트가 처리하고, 백엔드는 클라이언트가 전달한 **경로 좌표 리스트를 수신하여 저장** (Q10, 변경사항 반영)
- **FR-2.3** 코스 데이터 구성 (Q11):
  - 경로 (좌표 리스트)
  - 거리
  - 경로 중간의 관광지 / 편의시설 (외부 API 기반 표시)
- **FR-2.4** 코스 목록/상세 조회 API

### FR-3. 러닝 실행 / 기록 (Run Record)
- **FR-3.1** 실시간 GPS 추적(위치/경로/시간/페이스)은 **iOS 클라이언트**가 수행 (Q9=A)
- **FR-3.2** 백엔드는 **완료된 러닝 데이터**만 수신하여 저장 (실시간 소켓 연결 없음 — Q9)
- **FR-3.3** 사용자별 러닝 기록 저장 및 조회

### FR-4. 장소 추천 (Places / Recommendation)
- **FR-4.1** 먹거리·편의시설·관광지·음식점 정보는 **공공데이터포털 API** 기반 (Q12=A)
- **FR-4.2** 추가 예정 파일 데이터 소스 (Q12, Q13). **파일 데이터는 사용자가 직접 나중에 추가** (초기 구축 범위 밖):
  - 행정안전부 전국공중화장실 데이터
  - 군산시 가로등 현황
  - 군산시 약국 현황
  - 군산시 모범음식점 / 착한가격업소 (배지용)
- **FR-4.3** 러닝 후 먹거리 추천은 **도착 지점 기준 반경 1km** 이내 근접성 기준 (Q13=A, 반경 값은 추후 조정 가능)
- **FR-4.4** 모범음식점 / 착한가격업소에 해당하는 가게에는 **배지(badge)** 표시 (Q13)
- **FR-4.5** 코스 경로 상/도착지 주변의 편의시설·관광지 표시

### FR-5. 관리자 (Admin) — 이번 범위 밖
- **FR-5.1** 관리자 페이지/기능은 **이번 사이클에 포함하지 않음** (변경사항 반영). 운영자 공식 코스 및 장소/파일 데이터는 사용자가 **직접(DB 시딩 등)** 적재
- **FR-5.2** 향후 관리자 페이지가 필요해지면 별도 사이클에서 역할 분리 및 관리자 API 도입 검토

### FR-6. 공통 (Cross-cutting)
- **FR-6.1** API 응답은 **공통 응답 래퍼** 사용. 성공(success)/실패(failure)로 구분 (Q6=A, 변경사항 반영):
  - 성공 시 반환할 데이터가 있으면 **데이터를 담아 응답**
  - **HTTP status code를 의미에 맞게 적극 활용** — 예: 데이터가 있는 성공은 `200 OK`, 반환할 본문이 없는 성공은 `204 No Content` 등 상황별로 적절한 코드 사용
  - 래퍼 구조는 이 원칙(성공/실패 + status code 활용) 위에서 설계 단계에서 확정
- **FR-6.2** 전역 예외 처리 (실패 응답도 상황에 맞는 HTTP status code로 반환)

## 4. Non-Functional Requirements (비기능 요구사항)

### NFR-1. 보안 (Security) — Security Baseline 확장 활성화
- **NFR-1.1** 인증/토큰을 다루므로 SECURITY 규칙을 blocking 제약으로 적용
- **NFR-1.2** 단, **인증이 불필요한 공개(public) API**가 존재할 수 있음. "deny by default + 명시적 공개 예외" 원칙(SECURITY-08)을 따르며, 공개 엔드포인트는 명시적으로 나열·정당화 (Q-Security=X)
- **NFR-1.3** JWT 시크릿 등 민감정보는 환경변수로 관리

### NFR-2. 외부 연동 (Integration)
- **NFR-2.1** 공공데이터포털 API (장소/먹거리/편의시설/관광지)
- **NFR-2.2** 카카오 / 애플 소셜 로그인
- **NFR-2.3** 파일 기반 데이터 적재 (공중화장실, 가로등, 약국, 모범음식점, 착한가격업소) — 사용자가 직접 나중에 추가
- **NFR-2.4** 외부 API 추가 가능성을 고려한 확장 가능한 연동 구조
- **NFR-2.5** Tmap API는 사용하지 않음 (경로 생성은 클라이언트가 처리)

### NFR-3. 데이터 (Data)
- **NFR-3.1** MySQL (영속 저장) + Redis (토큰/캐시)
- **NFR-3.2** 좌표/경로 등 공간 데이터 저장 및 근접성 질의 지원 필요

### NFR-4. 테스트
- **NFR-4.1** 속성 기반 테스트(PBT)는 이번 사이클에서 **생략** (외부 API 연동 + 단순 CRUD 위주 — PBT=C). 추후 요청 시 도입

### NFR-5. 유지보수 / 설정 정리
- **NFR-5.1** 로거 설정 수정: `logging.level.com.celdog` → `com.ppip` (Q5)
- **NFR-5.2** JWT 라이브러리 의존성 추가 (현재 build.gradle에 미선언 — Q5)
- **NFR-5.3** 스키마 마이그레이션 도구(Flyway/Liquibase)는 **이번엔 도입하지 않음** (사용자 판단 보류 — Q5=A). 아래 부록 참고

## 5. Out of Scope (이번 범위 밖)
- 자체 이메일/비밀번호 회원가입
- 소셜 커뮤니티 기능 (리뷰, 팔로우, 피드, 코스 공유)
- 실시간 소켓 기반 러닝 추적 (클라이언트가 처리)
- 칼로리 기반 먹거리 추천
- 전라도 외 지역 확장
- 스키마 마이그레이션 도구 도입
- **관리자 페이지/기능** (이번엔 미포함, 데이터는 직접 적재)
- **Tmap API 연동** (경로 생성은 클라이언트가 처리)
- **파일 데이터 초기 적재** (사용자가 직접 나중에 추가)

## 6. Key Requirements Summary (핵심 요약)

1. **인증**: 소셜 로그인(카카오/애플) + JWT(Access 24시간 / Refresh 7일, Refresh는 Redis)
2. **코스**: 운영자 공식 코스 조회 + 사용자 직접 생성(경로 좌표 리스트 수신, Tmap 미사용)
3. **러닝 기록**: 클라이언트가 추적 → 백엔드는 완료 데이터 저장
4. **추천**: 공공데이터포털 기반, 도착지 반경 1km 먹거리 추천 + 배지 (파일 데이터는 추후 직접 추가)
5. **관리자**: 이번 범위 밖 (데이터 직접 적재)
6. **공통**: 공통 응답 래퍼(성공/실패 + HTTP status code 적극 활용, 200/204 등) + 전역 예외 처리, Security Baseline 적용(공개 API 예외 허용)

## 부록 A. 스키마 마이그레이션 도구란? (Q5 설명 요청 답변)

**스키마 마이그레이션 도구(Flyway / Liquibase)** 는 데이터베이스 테이블 구조(스키마)의 변경 이력을 **버전 관리**하는 도구입니다.

- **문제 상황**: JPA의 `ddl-auto`(create/update)는 개발 초기엔 편하지만, 운영 환경에서 테이블을 자동 변경하면 데이터 손실·예측 불가 문제가 생깁니다. 또 "누가 언제 어떤 컬럼을 바꿨는지" 추적이 안 됩니다.
- **해결**: 마이그레이션 도구는 `V1__create_user.sql`, `V2__add_course_table.sql` 처럼 **SQL 변경 스크립트를 버전별 파일**로 관리합니다. 앱이 시작될 때 아직 적용 안 된 스크립트를 순서대로 실행하고, 적용 이력을 별도 테이블에 기록합니다.
- **장점**: 팀원 간 DB 구조 동기화, 배포 시 안전한 스키마 변경, 롤백/이력 추적.
- **Flyway vs Liquibase**: Flyway는 순수 SQL 기반으로 단순·직관적. Liquibase는 XML/YAML/JSON으로도 변경을 정의할 수 있어 유연하지만 다소 복잡.

> **이번 결정**: 지금은 도입하지 않고 JPA 기본 방식으로 진행합니다. 도메인 스키마가 안정화되고 운영 배포가 가까워지면 그때 Flyway 도입을 권장합니다. 원하시면 그 시점에 다시 논의하겠습니다.
